# Present information (any stack)

Use `$vl-present` in Codex when discovered, or read and apply this source.
Other hosts use their supported invocation or the same source-read fallback.
This companion selects a presentation; it does not activate a seat or expand
publication, messaging, implementation or deployment authority. Read and apply
[vl-adhd](../vl-adhd/SKILL.md) as the sole shared writing policy for all prose
and labels. Preserve its complete-record and explicit-format precedence.

## Selection

Use the task, explicit operator format, facts/evidence, audience, delivery surface
and actual available capabilities as inputs. An explicit format wins within
existing authority and higher-priority instructions. Keep a text-only request
text-only. Do not add visual dependencies or change its output contract.

Otherwise choose the smallest format that improves comprehension:

| Need | Default presentation | Keep it useful |
| --- | --- | --- |
| Direct answer or short status | Prose | Lead with the outcome/action and preserve uncertainty. |
| Fixed comparable attributes or options | Table | Keep units, costs, exclusions and unknowns in the same comparison. |
| Relationships, architecture or flow | Editable diagram source plus text equivalent | Match every node and arrow to supplied facts; do not invent topology or guarantees. |
| Exploring changed inputs, derived results or useful navigation | Interactive view when supported | Start with a meaningful state; expose assumptions and the effect of each input. |

Interaction must improve understanding, not decorate a simple answer. Do not
use blanket HTML or generate an artifact for every update. A raster illustration
is different from an editable conceptual diagram. Route actual bitmap requests
to an available image capability. Route Word/PDF artifacts and exportable
scientific figures to the actual document/plotting specialist contract. Do not
substitute a screenshot for required editable or exportable source.

Read the [illustrative examples](references/examples.md) for the applicable case.
They describe expected behavior, not observed host support or live project evidence.

## Capabilities

Discover the tools and skills actually exposed in the current host. Read the
selected capability's full instructions before producing its output. Check the
accepted input, output surface, file/location rules, sandbox and verification
methods. Use one compatible provider recipe for the selected path. A skill being
installed does not prove rendering support, and another host's recipe is not a
bridge. Do not combine incompatible canvas, fragment or document recipes.

Reuse a usable capability. If its SDK, path, viewer or required tool is unavailable
or unverified on this host, state that exact limitation and use a readable fallback.
Do not invent a Windows bridge, browser executor or universal inline HTML support.
A generic browser tool does not prove that a particular host visualization executes.
Renderer installation, new dependencies, telemetry, server launch, deployment and
public publication are not prerequisites. Do not start a shared site to manufacture
rendering proof. Respect the task's scope and any existing stop conditions.

## Clarification

Make routine choices automatically from the inputs above. Ask only when an
unresolved delivery, usability or maintenance choice materially changes the result
and cannot reasonably be inferred. State the choice and its practical effect in
one focused question. Use the existing question/approval rules; presentation does
not create a new permission requirement. A missing rendering capability calls for
an honest fallback, not an unnecessary preference question.

## Evidence

Treat the owning issue/spec as the source of decisions and state. Link the visual
and its explanation to those records; do not make a second tracker. Preserve exact
facts, qualifiers, constraints, costs and necessary literals in the selected view.
Name source assumptions and distinguish observations from illustrative or derived
values. Keep units and labels consistent with the text equivalent.

If a visual sandbox restricts links, put evidence links in adjacent prose. Do not
bypass its restrictions or omit the evidence. Presentation-only inputs change the
view, not the owning issue, product state, authorization or settled decision.

## Verification

Compare source facts with every table cell, diagram node/arrow and derived result.
Check the initial state, a meaningful changed input and stated assumptions. Verify
that the text equivalent preserves essential facts and evidence limits.

Use the selected capability's permitted inspection path. For interactive output,
actually exercise the primary input and derived result, focus/keyboard operation,
narrow width and reduced-motion behavior where available. Record observed checks
separately from source inspection. Source presence, metadata tests or a diagram
parser cannot establish rendering, interaction or keyboard acceptance. Report an
unperformed check as not exercised/unverified. Report unsupported behavior only
when the actual tool/provider contract or an observed failure establishes the limit.

If inspection or rendering fails, retain usable facts/source and report the precise
failure or unavailable inspection path. Follow existing repair/handoff rules; do
not silently reset attempts or increase authority to force a visual to work.

## Fallback

Provide useful prose or a table when a render path is unavailable, unverified or
fails. For a flow, retain editable diagram source with a complete text explanation.
For a scenario, show the initial and changed cases with derived values and assumptions.
State the actual limitation: for example, a required SDK/path is unavailable, or
interaction/keyboard checks were not exercised. Do not generalize this to all hosts.

A readable fallback preserves the task's essential facts, evidence and next action.
If a required deliverable cannot be produced, name the unmet format requirement;
do not claim that source inspection completed it. No external deployment or new
server is required to deliver that honest result.

## Accessibility

Keep a sensible reading order and a readable text equivalent. Use named native
controls and visible focus for interactive input. Verify keyboard operation rather
than infer it from markup. Keep essential facts visible without hover. Pair color
with labels or another non-color cue; color alone must not carry meaning.

Support narrow widths with wrapping or reflow. Respect reduced-motion preferences
and keep essential content available with motion disabled. Animation may explain a
transition, but essential facts must not exist only in animated content. Follow the
selected capability's accessible-control and layout constraints. Report actual
accessibility checks and their limits; a checklist is not runtime proof.
